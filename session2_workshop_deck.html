Session 2 · Concept

The problem we are going to solve

A ticket is a saved support request. It has an owner, a number, a summary and an open or closed status.

The legitimate task

Alice asks for help with registration. She creates a ticket, opens it and closes it when the issue is resolved.

The security failure

Alice asks for Bob’s ticket number. The application returns Bob’s private request because it checks the number but not the owner.

Our goal: keep Alice’s legitimate actions working while refusing actions she is not allowed to perform.

Session 2 · Concept

MCP can use local pipes or HTTP

Location and transport are different choices: a server running on your own computer can also use HTTP.

This project: local stdio

The client starts a Python child process. It writes protocol messages into a pipe and reads replies from another pipe.

No MCP HTTP port or URL is opened. The token is supplied in the child’s environment.

Another deployment: Streamable HTTP

The client sends MCP requests to an HTTP endpoint. That server can be local or remote.

A protected remote deployment uses HTTPS and the MCP HTTP authorization flow. Access tokens travel in authorization headers.

“MCP server” does not automatically mean a remote website. Transport describes how the messages travel; authorization describes who may use the server.

Protocol reference: MCP transports · HTTP authorization.

OAuth lets a user delegate access

Learn the roles first. Then compare them with the smaller flow implemented for this workshop.

Resource owner

Alice owns the access being delegated.

Client

The assistant application asks to act for her.

Authorization server

Handles consent and issues a token.

Resource server

MCP validates the token before serving a request.

  1. The client requests specific access. Alice approves or denies it.
  2. A real OAuth flow obtains an access token through a defined protocol exchange.
  3. The client presents that token to the intended resource server.
  4. The resource server checks the token and permissions; the application still checks record ownership.
The client does not need Alice’s website password. OAuth delegates access; it does not replace all application authorization.

Session 2 · Concept

What our simulation implements

The simulation teaches user consent, limited access, expiry and revocation without building an identity platform.

Visible consent and a real access check

Sign in → Assistant → Authorize assistant.

Select permissions and 1, 5 or 30 minutes. Allow or deny. Replace or revoke the grant later.

The actual MCP process rejects unauthorized operations.

A deliberately smaller protocol

The website issues a random token directly after consent. It keeps the grant and token hash in SQLite.

No external authorization provider, discovery, authorization-code exchange, PKCE or refresh-token flow is implemented.

Call this a workshop simulation of OAuth-style consent and delegation. Do not call it a complete OAuth implementation or the standard MCP HTTP authorization flow.

Session 2 · Concept

The client presents a token to MCP

There is an authenticated client-to-MCP boundary. There is no second network login between MCP and this local ticket-service module.

ConsentAlice approves→Grant record + token hash→Client token in HttpOnly cookie
MCP callWebsite’s MCP client→MCP_ACCESS_TOKEN in child environment→MCP validates it
Ticket operationMCP derives Alice from grant→ticket_service.execute(actor, proposal)
MCP does not present another credential to the ticket service. Here that service is an imported Python module in the MCP process. The server passes the validated user object into a function. Django then uses its configured database connection.

If the ticket service becomes a separate HTTP API, it needs its own authorization design. Do not blindly forward an MCP access token to another audience.

The token is not an LLM argument. Alice’s login password is not the MCP credential.

Session 2 · Concept

Which shortcuts must not become a production design?

Workshop choiceWhat a production design needs
Direct token issuance after a local consent formA maintained authorization provider and the appropriate OAuth/MCP flow; PKCE where required
One-time token display for terminal teachingControlled credential delivery; no tokens in screenshots, prompts or logs
Debug exposes actual model promptsRestrict diagnostics and redact secrets; avoid exposing sensitive context
Local HTTP development websiteHTTPS and appropriate secure-cookie settings for deployment

These are scope limits or deployment shortcuts, not all the same kind of vulnerability. Local stdio and direct Python service calls are legitimate designs; they do not create a security sandbox.

get_ticket schema
Expanded get_ticket branch from tickets/schema.py
{
  "type": "object",
  "required": ["tool", "arguments"],
  "additionalProperties": false,
  "properties": {
    "tool": {"const": "get_ticket"},
    "arguments": {
      "type": "object", "required": ["ticket_id"],

        "type": "integer", "minimum": 1
      }}
    }

Read each rule literally
required: these fields must exist.
const: this action name must be get_ticket.
type: integer: the ID must be a whole number, not text or a boolean.
minimum: 1: the number must be positive.
additionalProperties: false: reject extra fields at both object levels.
A request for Bob’s ticket can satisfy every rule shown here. The next security decision is whether the authenticated user is permitted to read that record.

Session 2 · Before Exercise 8
What is NeMo Guardrails?


NVIDIA’s open-source Python library for adding programmable checks to AI applications. It is released under the Apache 2.0 license.


What a guardrail does
A guardrail is a configured check or workflow. For example: reject an instruction-override attempt, inspect a proposed tool call, or check a response for exposed credentials.
The application sends content through those checks and handles the result.


How it makes a decision
A check can use ordinary Python rules, a specialized detector, an LLM, or an external service. The developer chooses and configures the checks.
Our Demo mode uses programmed rules. Semantic mode also asks local Qwen to judge the content.


Here, “NeMo” means NeMo Guardrails. It runs as application software around model interactions; configuring a guardrail does not retrain the model or replace ticket-permission checks.


Sources: NVIDIA repository · Apache 2.0 license.


Session 2 · Before Exercise 8
Inside the worker: configuration → flow → check


1 · Load configuration
RailsConfig reads YAML settings and Colang flows. The settings select which named checks run.


2 · Run the flow
LLMRails processes the request through the active flow. Colang specifies the steps and what happens after a check.


3 · Call an action
The flow calls a registered Python function. Our function applies rules and, in semantic mode, asks Qwen too.


4 · Return the result
A failed check triggers the flow’s refusal and stop. Our worker reports allowed: false; the app stops that assistant action.


Trace the actual code: guardrails/worker.py loads runtime.yml and runtime.co, registers check_workshop_policy, and calls generate_async. The action calls the policy functions in policy.py.


Our integration: input, tool proposals, tool results and replies are sent to this worker as separate checks. All use its configured NeMo input rail; the JSON stage field identifies the content being checked. The worker checks content; the main application generates chat replies.


NVIDIA: architecture and runtime. The sequence above describes this project’s implementation.

SAST is the activity. These are two tools.
SAST
Static Application Security Testing examines source code for unsafe patterns.
It complements browser demonstrations and automated request tests.
Bandit
Inspects Python code using syntax analysis and security plugins.
It can flag risky calls such as unpickling untrusted input.
Semgrep
Matches code against rules. This project supplies local rules for unsafe deserialization and unchecked file paths.
Its report names the rule and source location.

Session 2 · Takeaways
The model stayed untrusted. The application gained rules.
Before repairs
  • Invalid requests slip through a direct path.
  • A valid ticket number can reveal another user’s record.
  • A closure request executes without the required human decision.
  • File input can trigger code or escape its directory.
After repairs
  • Exact schema checks run before dispatch.
  • Ticket operations check the authenticated owner.
  • Closure is pending until a bound, expiring, one-use confirmation.
  • Imports use JSON; downloads stay with the correct ticket.
Consent and token checks were provided infrastructure in both versions. They limited the assistant’s operations; they did not repair the missing ticket rules for you.
